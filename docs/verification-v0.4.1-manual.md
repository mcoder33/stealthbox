# Ручная проверка v0.4.1 — 2 октября 2026

Основные сценарии подключения, переноса исходников и обоих исполнителей
прошли, но при очистке обнаружен критический сбой системного tmux 3.4:
удаление тестовой сессии обрушило общий сервер и завершило также старую
shell-сессию пользователя. На этой ВМ установлен tmux 3.7c, с которым сбой
не воспроизвёлся в 20 повторениях; подключение затем проверено снова вручную.
Потеря прежней shell-сессии остаётся отдельным отрицательным результатом проверки.
Найдены также три недочёта диагностики и предпросмотра, перечисленные ниже.
Полный сценарий с запросом к модели не проверен: на ВМ нет авторизации агентов.
Исходный код приложения и версия Stealth Box в этом прогоне не изменялись.
Окружение ВМ изменено: для устранения сбоя установлен tmux 3.7c.

## Среда и способ проверки

- Установленный `stealthbox v0.4.1`, commit `f92331e48df1e6bc8c20d59e56f31d517afd884a`.
- Локальный Mac ARM64; существующая Ubuntu ВМ в Yandex Cloud Kazakhstan, `kz1-a`.
- Реальные SSH, tmux 3.4 → 3.7c, rsync, Docker Compose и отдельный обратный Unix-socket мост.
- Команды и клавиши вводились в настоящий PTY: TUI, окна, панели, агенты,
  отключение SSH. Это самостоятельный ручной прогон; `make e2e` его не заменял.
- Размеры терминала: 120×36, 100×30, 80×24. Основной TERM — `xterm-ghostty`.
- Управление приложением Ghostty отклонено инструментом Computer Use.
  Поэтому точное отображение шрифтов, мышь, буфер обмена и вид нативного окна
  по скриншоту не подтверждены. Проверены реальный поток терминала и содержимое панелей tmux.
- Созданы отдельные конфиг, сессия `sb-manual-20261002`, корни исходников и прогонов.
  Рабочая сессия пользователя не использовалась для ввода команд.

## Найденные замечания

Три замечания к Doctor, метаданным MCP и connect dry-run пока не исправлены
в коде приложения. Изменение tmux выполнено только в окружении существующей ВМ.

### Критический: tmux 3.4 падает при удалении сессии с увеличенной панелью

При адресном удалении `sb-manual-20261002` команда `kill-session` завершилась
с `server exited unexpectedly`. Вместе с тестовой сессией завершился общий
сервер `tmux -L stealthbox` и прежний пользовательский shell PID 7049.
Команды в пользовательскую сессию не вводились, но отдельного имени сессии
оказалось недостаточно для изоляции от падения общего сервера.

В Ubuntu Apport зафиксирован SIGABRT процесса `/usr/bin/tmux`, пакет
`3.4-1ubuntu0.1`; backtrace показывает `free(): double free detected in tcache 2`.
Сбой воспроизведён ещё дважды на отдельных socket: с пустым конфигом и с
пользовательской темой. Минимальный сценарий — две сессии, split и zoom во второй,
затем удаление второй: первая тоже исчезает. Stealth Box и агенты для этого не нужны.

Пользовательская сессия создана заново в `/home/dev/Projects`. Файлы и ВМ
сохранены; восстановить прежний процесс shell нельзя.

Собран [официальный релиз tmux 3.7c](https://github.com/tmux/tmux/releases/tag/3.7c).
SHA-256 архива совпал с digest GitHub:
`7c60cae9a0e25288e2e24750aafc9e8800fc7fd4555e447e1b29ee4201cfb3bf`.
До установки выполнены 10 повторений минимального сценария без темы и ещё 10
с пользовательской темой, каждый на отдельном socket. Все 20 сохранили PID shell
соседней сессии. Это подтверждение относится к проверенной версии и сценарию;
оно не является гарантией для других версий tmux.

Бинарник установлен в `/usr/local/bin/tmux`, системный `/usr/bin/tmux` 3.4 сохранён.
Перед заменой созданной мной пустой сессии проверены её PID, cwd, отсутствие
zoom и подключённых клиентов. Новый рабочий сервер — 3.7c, PID 33314;
shell — PID 33317. Затем обычная команда `stealthbox` открыла настоящий PTY,
`pwd`, `codex --version`, `claude --version` отработали, detach сохранил shell.
В новой версии темы пропущена одна неподдерживаемая настройка вместо 19 в 3.4.
Команда через основной мост к Mac вернула Darwin; bridge-status и doctor успешны.

На этой ВМ сбой устранён переходом на проверенную версию. Автоматическая
подготовка другой Ubuntu ВМ по-прежнему может установить tmux 3.4 из её пакетов:
проверку/выбор безопасной версии в коде Stealth Box ещё нужно добавить.

### 1. Doctor пропускает неработоспособный путь локального исполнителя

При `runner_root=/tmp/sb-manual-20261002/runners` на macOS диагностика возвращает
все `OK`, но первый локальный прогон заканчивается:

```text
Mac runner: HTTP 400: runner path contains symlink: /tmp
```

`/tmp` на macOS — ссылка на `/private/tmp`. Сам запрет ссылок соответствует
защите исполнителя; недочёт — отсутствие ранней проверки в `doctor`.
После изменения тестового профиля на `/private/tmp/...` локальные прогоны работают.
Рекомендуемое исправление: проверять компоненты `runner_root` при диагностике
и показывать понятную рекомендацию использовать физический путь.

### 2. MCP объявляет устаревшую версию сервера

`initialize` реально установленного v0.4.1 возвращает:

```json
{"serverInfo":{"name":"stealthbox","version":"0.3.0"}}
```

В `internal/stealthbox/mcp.go` версия зафиксирована строкой. Исполнение инструментов
работает; неверны метаданные, используемые при диагностике. Версию нужно брать
из `BuildVersion`.

### 3. Connect dry-run принимает неизвестного исполнителя

```sh
stealthbox connect --runner nonsense --dry-run
```

Возвращает успешный предпросмотр с `runner=nonsense`. Реальный `connect` с тем же
значением правильно отклоняет его: `root workspace runner must be local or vm`.
Предпросмотр должен использовать ту же проверку аргументов до вывода плана.

## Тяжёлый прогон Zadolbator

Использованы 3743 отслеживаемых файла из рабочей копии на основе
`84b9d78c67e17985aae6aaa6419591f42e813702`.
Секретные локальные конфигурации, `.env`, настройки агентов и зависимости
не переносились на ВМ. Тестовая копия получила отдельные Development-конфигурации,
фиктивные учётные данные и fixture-запись DNS для `dns.quad9.net`.
Рабочие файлы Zadolbator не изменялись.

Реальная цепочка: tmux на ВМ → `stealthbox run --runner local` → rsync → Docker Mac.
Тестовые PostgreSQL 15, Redis и ClickHouse 25.8 работали в отдельной внутренней
Docker-сети без опубликованных портов. PHP AMD64 исполнялся на Mac ARM64.
Миграции выполнены в новых тестовых базах.

| Набор | Тесты | Assertions | Результат |
|---|---:|---:|---|
| common/unit | 1125 | 5225 | exit 0, 2 incomplete |
| api | 105 | 239 | exit 0 |
| frontend | 8 | 15 | exit 0 |
| backend/unit | 16 | 24 | exit 0 |
| **Всего** | **1254** | **5503** | **0 failures, 0 errors, 2 incomplete** |

Числа подтверждены XML, скачанными с Mac обратно на ВМ через `stealthbox fetch`.
Два incomplete в XML представлены как skipped; они не считаются успешно выполненными.
Inode и mtime `vendor/autoload.php` сохранились после всех четырёх прогонов.
На самой ВМ выполнен Docker smoke, тяжёлые PHP-наборы запускались на Mac.

При подготовке тестовой копии исправлены две ошибки самого стенда: явный
`platform: linux/amd64` не принимался для существующего локального image ID;
удалённый каталог шаблонов `environments/prod` вызывал цикл предупреждений в
Yii init. Убран лишний platform, добавлены пустые каталоги шаблонов. Код и проверки
приложения ради результата не менялись.

## Ограничение отмены Docker

Отмена процесса Docker CLI не гарантирует остановку контейнера в Docker daemon.
При отмене зависшего Yii init тестовый контейнер продолжил работать и был остановлен
отдельной адресной командой. Для таких прогонов нужен явный `docker compose down`
или остановка конкретного контейнера. Автоматического повтора команды не было.

## Что осталось непроверенным

- Запрос к моделям и вызов MCP по решению настоящего агента: оба аккаунта на ВМ
  не авторизованы. Запуск интерфейсов и прямые MCP-вызовы подтверждены отдельно.
- Нативное окно Ghostty, мышь, clipboard, фактическое отображение шрифтов.
- Windows/WSL2 на реальном Windows-компьютере; в этом прогоне использовались Mac и Linux ВМ.
- Сон Mac, физическая потеря сети, перезагрузка/прерывание ВМ. Проверялся разрыв
  конкретного SSH-сеанса и остановка отдельного тестового моста.
- Копирование личных shell-плагинов, MCP-конфигураций и аккаунтов не входит
  в подтверждённое поведение подготовки среды.

## Очистка и доказательства

Тестовый Compose-проект, его сеть, сети Alpine, тестовая tmux-сессия, мост и
каталоги исходников/прогонов удалены. Существующая казахстанская ВМ сохранена.
Прежняя рабочая сессия пользователя завершилась из-за описанного выше сбоя tmux;
текущая новая — `stealthbox | %0 | PID 33317 | bash`, сервер tmux 3.7c.
Основной Mac bridge не останавливался и проверен online после восстановления.

Локальные записи PTY, снимки панелей, логи и четыре XML сохранены в
`~/.local/share/stealthbox/manual-qa-20261002/`.
Они относятся к этому прогону v0.4.1, а не к историческим проверкам v0.3/v0.4.0.
