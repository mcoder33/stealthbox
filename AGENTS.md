# Stealth Box для агента

## Если пользователь сказал «установи»

Веди установку сам, от обнаружения существующей среды до проверки выбранных проектов. Команды ниже выполняй в терминале пользователя. Если есть только ссылка на репозиторий, открой README и эту инструкцию.

1. Проверь ОС, установленный бинарник и версию, действующий профиль и настроенные SSH-алиасы. Используй уже названные пользователем параметры. Покажи подходящие варианты, если выбор неоднозначен. Если SSH ещё не настроен, уточни адрес, пользователя и при необходимости промежуточный хост; настрой и проверь соединение. Приватный ключ и токены остаются на машине пользователя.
2. До подготовки профиля уточни только недостающее: какая ВМ, где выполнять тяжёлые задачи (на компьютере пользователя или на ВМ) и какой агент нужен (Claude, Codex или оба). Объясняй выбор обычными словами. Для уже занятого профиля с другой ВМ создай отдельный профиль. Во всех дальнейших командах используй выбранные бинарник и конфиг.
3. Выполни подготовку среды и проверку входа по разделу ниже. Если требуется подтверждение в браузере, дай пользователю точную команду и укажи, где её выполнить. После ответа повтори проверку и продолжи с проектами.

## Установить и проверить

1. На компьютере пользователя определи путь к бинарнику, проверь `stealthbox --version` и выбери профиль. CLI использует `STEALTHBOX_CONFIG` или `~/.config/stealthbox/config.json`. Штатный установщик macOS/Linux кладёт проверенный бинарник в `~/.local/bin/stealthbox`. Если PATH или профиль отличаются, используй абсолютный путь и проверяй ту же пару «бинарник + профиль», которую открывает пользователь. [Установка macOS/Linux и Windows](README.md#быстрый-старт-весь-projects).
2. Проверь SSH-алиас (`ssh -o BatchMode=yes dev-vm 'uname -sm'`) и `rsync`. Для нового профиля выполни на компьютере `stealthbox setup --host dev-vm --runner local`. Для существующего используй `stealthbox setup` с его конфигурацией. Для Docker-прогонов выполни `docker info` на выбранном компьютере или ВМ. В Windows выполняй SSH и проверку локального Docker в выбранном WSL2.
3. Открой `stealthbox` в обычном терминале вне локального tmux. Для `local` подключение запускает мост. Без интерактивного подключения выполни `stealthbox bridge-start` на компьютере и дождись подтверждения доступа с ВМ. Затем выполни `stealthbox doctor`. У каждого одновременно работающего моста должен быть свой `bridge.socket`.
4. Проверь выбранного агента с компьютера через `stealthbox auth-status --agent codex` или `--agent claude`. Для своей команды запуска проверь статус через неё на ВМ с аргументами `login status` или `auth status`. Если требуется вход, пользователь сам запускает сценарий входа агента **на ВМ** и завершает его в браузере. [Вход Codex и Claude](README.md#4-войди-в-аккаунт-и-запусти-агента).
5. После проверки аккаунта переходи к выбору и переносу проектов.

## Выбрать проекты, перенести файлы и проверить результат

1. Покажи найденные проекты под `local_root` на компьютере и под `vm_root` на ВМ (для ВМ используй `stealthbox list --discover` на компьютере). Показывай относительные пути, чтобы различать одноимённые репозитории. Спроси, с какими проектами пользователь хочет работать. Если он уже их назвал, проверь эти пути сразу. Можно выбрать несколько проектов или отложить перенос.
2. Для каждого выбранного проекта установи, где лежит нужная рабочая копия. Если проект уже готов на ВМ, сразу переходи к проверке раннера. Если нужные изменения на компьютере, предложи импорт на ВМ. Если нужны изменения с ВМ в основной локальной копии, предложи экспорт. Когда обе стороны содержат свои изменения, покажи различия и уточни направление. Для нового Git checkout с историей сначала клонируй согласованный репозиторий в каталог назначения: перенос файлов исключает `.git`.
3. На компьютере задай `project` равным выбранному пути относительно корня, например `team/api`. Для каждого проекта создай **отдельный план** вне checkout:

   ```sh
   plan="$(mktemp -d)/sync.json"
   stealthbox source import --path "$project" --plan "$plan"
   ```

   Для обратного направления замени `import` на `export`. Покажи источник, назначение, добавления и перезаписи по каждому плану. После подтверждения примени каждый согласованный план командой `stealthbox source apply --plan "$plan"` с соответствующим файлом. При конфликте обнови предпросмотр. По умолчанию сохраняй файлы, которые существуют только у получателя. [Правила переноса и исключения](README.md#rsync-исходников-только-по-явному-запросу).
4. В управляемой оболочке на ВМ для **каждого выбранного проекта** выполни `stealthbox run --path "$project" -- pwd` (задай там тот же относительный путь). Из MCP-сессии эквивалентен `runner_run` с этим `path` и `argv: ["pwd"]`. В режиме `local` этот вызов впервые синхронизирует проект в отдельную копию раннера. Проверь нулевой код, ожидаемый checkout, исполнитель и `sync: "completed"` в результате. В режиме `vm` ожидается исполнение на ВМ. Если проверка дала ошибку, укажи конкретный проект и причину.
5. Заверши коротким итогом: ВМ, выбранный раннер, состояние входа, куда перенесён и где проверен каждый проект. Дай готовую команду входа на компьютере с фактическим профилем и подскажи, в какой каталог на ВМ перейти и какую команду набрать — `claude` или `codex`.

## Работать с проектом

- Читай инструкции выбранного проекта на ВМ. Если работаешь из общего корня, узнай относительный путь через `projects_list` и сверь его с задачей. Для проверки без проекта используй отдельный тестовый каталог под корнем ВМ. Выбор первого попавшегося репозитория приведёт к копированию его файлов.
- Docker, сборки, установку зависимостей, тесты и полный линт запускай через `runner_run`. Передай `path` нужного checkout и команду как массив `argv`. По умолчанию используется раннер сессии. Для проверки профиля с Docker на компьютере вызови `{"path":"team/repo","runner":"local","argv":["docker","version"]}`, подставив выбранный проект. Проверь код завершения, сведения о Docker Server и строку `[execution]`: ожидаются правильный `checkout`, `runner: "mac"` и `sync: "completed"`. При сбое сообщи ошибку; после обрыва проверь состояние начатой команды перед повтором.
- Перед локальным прогоном раннер синхронизирует рабочее дерево выбранного проекта с отдельной копией на компьютере, включая незакоммиченные файлы с учётом фильтров. Для переноса изменений **между основными рабочими копиями** запускай на компьютере `source import` (компьютер → ВМ) или `source export` (ВМ → компьютер), просмотри план, затем `source apply`. [Команды и исключения](README.md#rsync-исходников-только-по-явному-запросу).
- Если пользователь вставил путь Mac к временному `pasted-image-*.png`, передай точный путь в `read_pasted_image` аргументом `path`. Инструмент возвращает изображение, включая JPEG для крупных снимков. Для проверки попроси агента прочитать короткую надпись, которая есть только на картинке. Если файл уже исчез, попроси вставить снимок заново.

## Обновить действующую установку

Обнови локальный бинарник выбранного профиля и выполни `setup` с этим же профилем. Если launcher передаёт `--binary`, обнови также указанный в нём Linux-бинарник под архитектуру ВМ. Перед перезапуском моста дождись окончания текущих прогонов: явный `bridge-stop` может их прервать. На компьютере выполни `bridge-stop` и `bridge-start` для нужного профиля. Используй эти подкоманды с бинарником Stealth Box.

Уже открытый Claude может продолжать использовать прежний MCP-процесс. Для обновления инструмента выбери `/mcp → stealthbox → Reconnect`. Для получения обновлённых стартовых инструкций запусти новую управляемую сессию агента. Проверь один реальный вызов через мост: `bridge-status` подтверждает только состояние локальной службы.
